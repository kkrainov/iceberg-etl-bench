# Methodology

Status: **Phase L, exploratory.** Thresholds are deliberately absent. They will be
pre-registered (published before running) for Phase C. Phase L results are labelled
exploratory wherever they appear.

## 1. Questions

| ID | Question | Kind |
|---|---|---|
| **Q1 Headroom** | Is DataFusion + datafusion-distributed faster and cheaper per query than Trino on the same hardware and Iceberg tables? | Go/stop input |
| **Q2 Distribution tax** | How much of single-node DataFusion's lead over Trino survives when execution is distributed? | Design input |
| **Q3 Memory behaviour** | At a fixed node size, how often does each engine complete, fail cleanly, or get killed under memory pressure, and do neighbouring queries survive? | Go/stop input |
| **Q4 Pain points** | Where does the time go (scan, exchange, compute, plan quality), and which upstream gaps matter most? | Design and upstream input |

Prior evidence (ClickBench single-node results, the datafusion-distributed README's
Trino comparison, native-vs-JVM engine studies) motivates the questions but is not
used as evidence. Its known weaknesses are summarised in the report.

## 2. Systems under test

| ID | System | Version (pinned in `versions.lock.yaml`) | Mode |
|---|---|---|---|
| `trino` | Trino | 484 (official image) | `retry-policy=NONE`. Phase L: single node. Phase C: dedicated coordinator + workers. |
| `df` | DataFusion, single process | 55.x via datafusion-distributed's lockfile | One process, no distribution layer |
| `dfd` | DataFusion + datafusion-distributed | 4.0.0 | Coordinator + N workers over Arrow Flight; any node can coordinate |
| `dfd-jo` | `dfd` with apache/datafusion#24456 (join-order enumeration) applied | Commit pinned | Suite A6 only; clearly labelled as unreleased code |

**Configuration rules**
- Trino is configured per its official documentation (JVM, memory, exchange,
  Iceberg connector). Every non-default setting is listed with a reason.
- DataFusion uses defaults except the memory pool and parallelism, which are set to
  match the hardware.
- Configurations will be offered to Trino and DataFusion maintainers for review
  before Phase C.

**Memory parity**
- Each engine node runs in a container with the same CPU and memory limit.
- DataFusion's memory pool limit equals Trino's `query.max-memory-per-node`.
- Trino's JVM heap and DataFusion's process overheads both live inside the same
  container limit.

## 3. Data

| Item | Choice |
|---|---|
| Datasets | TPC-H and TPC-DS, generated by Trino's `tpch` / `tpcds` connectors via `CREATE TABLE … AS SELECT` into Iceberg |
| Table format | Iceberg format version 2, Parquet, zstd. Trino's default target file size. Standard tables unpartitioned, to match prior published runs. |
| Derived ETL tables | `etl_sf<N>.*` built by deterministic SQL from TPC-DS: a Zipf-skewed key table and a duplicated-rows table for dedup. Fact-to-fact joins use `store_sales`/`store_returns` and `lineitem`/`orders` directly. Generation SQL is versioned in `datagen/`. |
| Statistics | **As real users run it.** Trino uses the statistics its Iceberg CTAS collects by default. DataFusion uses whatever it reads from Iceberg manifests and Parquet footers. The asymmetry is reported, not removed. |
| Catalog | Phase L: Iceberg REST (Lakekeeper). Phase C: AWS Glue. Both engines read the same tables through the same catalog. |
| Scale | Phase L: SF1 (smoke), SF10 (main). Phase C: SF100 (main), SF1000 (only if the rest of M0 passes). |

Data size and memory are scaled down together. SF10 with ~8 GiB per engine node has
roughly the same pressure ratio as SF100 with ~80 GiB.

Findings from building the data generator (Trino 484):
- TPC-DS `CHAR(n)` columns become Iceberg `string` (Trino `varchar`) in a plain CTAS,
  with no error and no cast needed, and their pad spaces are dropped (`'Dr.       '`
  is stored as `'Dr.'`). Both engines therefore read unpadded strings; the CHAR rule
  in section 8 stays as a safeguard. `varchar(n)` loses its length bound.
- Decimals (`decimal(7,2)`, `decimal(15,2)`, TPC-H `decimal(12,2)`), dates and
  integers map one to one. The `tpch` connector is configured for standard column
  names and DECIMAL money columns, as in the TPC-H spec (its defaults are unprefixed
  names and DOUBLE).
- Trino's `tpcds` connector generates 75 `reason` rows at every scale factor (spec: 35
  at SF1, 45 at SF10). Every other row count matches the TPC-H and TPC-DS specs.
- `etl` skew: power-law key with exponent 1.2; the top key holds about 14% of rows at
  every SF.

Open item: whether iceberg-rust reads every type and encoding Trino writes (step 3b).
Trino writes Parquet with INT32/INT64 decimals, `timestamp(6)` as INT64 micros, some
strings as `DELTA_LENGTH_BYTE_ARRAY`, and ~128 MiB row groups (about 16 per SF10
`lineitem`).

Every query in every suite is reported. Nothing is excluded because an engine failed
it.

### B1 catalogue (draft)

| ID | Class | Shape | Stresses |
|---|---|---|---|
| J1 | Join | Fact-to-fact `store_sales ⨝ store_returns` on (ticket, item) | Partitioned hash join |
| J2 | Join | `lineitem ⨝ orders`, all columns kept | Large build side |
| J3 | Join | Zipf-skewed key ⨝ dimension | Skew, straggler tasks |
| J4 | Join | Three-way fact join | Join order |
| G1 | Aggregation | `GROUP BY (customer, item)`, ~10⁸ groups at SF100 | High cardinality |
| G2 | Aggregation | `COUNT(DISTINCT)` on a high-cardinality column | Distinct state |
| W1 | Window | `ROW_NUMBER()` dedup over a skewed key, keep `rn = 1` | Buffering one hot partition |
| W2 | Window | `SUM() OVER (PARTITION BY customer)`, whole-partition frame | Buffers the full input |
| W3 | Window | Running frame with `ORDER BY` | Full sort inside a window |
| T1 | TopK | `ORDER BY … LIMIT 100` and `LIMIT 100000` | TopK; large-limit TopK approximates a full sort |
| S1 | Scan | Selective filter + projection + aggregate | Pruning, Parquet decode |
| S2 | Scan | Wide, non-selective scan + aggregate | Raw scan throughput |

- Every B1 query ends in an aggregate or a small result, so transferring results to
  the client doesn't dominate the timing.
- **Full sorts** are measured through windows (W1, W3) and large-limit TopK (T1),
  because writes are out of scope.

### B2 memory levels

Data stays fixed. The engine node's memory budget steps down together (container limit,
Trino `query.max-memory-per-node` and DataFusion pool, all scaled by the same factor):
**100% → 50% → 25%** of the baseline. Each B1 query is run once per level, plus
one hot repeat when it succeeds.

## 5. Run protocol

- **Isolation.** One query at a time, except in B3. Engines never run at the same time.
  Each engine's containers are stopped while the other engine runs.
- **Cold run.** The first execution after an engine restart and a page-cache drop on
  the host (Phase L), or after an engine restart (Phase C, S3 has no local cache).
  Each engine's own metadata and file caches are left at their defaults and
  documented.
- **Hot runs.** 5 runs after the cold run. Report the median plus min/max.
- **Order.** Engine blocks alternate (ABBA). Query order within a block is shuffled
  with a recorded seed.
- **Timeout.** 600 s per query (Phase L), recorded as an outcome rather than an error.
- **Restarts.** An engine is restarted after any `killed` or `unresponsive` outcome
  before continuing, and the restart is logged.
- **Investigations don't change baselines.** Configuration changes made while
  investigating a failure become named engine variants with their own runs. Cells hit
  by a harness or environment fault are marked invalid and re-run; they are never
  counted as engine outcomes.
- **Machine hygiene.** Same power plan, background activity paused, environment
  manifest captured per run (see the infrastructure doc).
- **Repeats.** Phase C runs the main suites on two independently launched clusters.

## 6. Metrics

| Metric | Source | Notes |
|---|---|---|
| Wall time | Harness client clock, the same code path for every engine | Primary metric. Both engines run as long-lived servers, so client startup time is excluded (the ClickBench timing flaw). |
| Engine elapsed | Trino query stats; DataFusion runner | Cross-check |
| CPU-seconds | cgroup v2 `cpu.stat` `usage_usec` delta per node | Summed across nodes |
| Peak memory | cgroup v2 `memory.peak`, reset before each query (kernel ≥ 6.12); 10 Hz `memory.current` sampling as fallback | Per node and maximum across nodes. Also the engine-reported peak (Trino peak reservation, DataFusion pool high-water mark). |
| OOM kills | cgroup `memory.events` `oom_kill`, container exit code 137 | Used for outcome classification |
| Result fingerprint | Row count + order-insensitive hash of the normalised result | See section 8 |
| Breakdown (A5) | datafusion-distributed task metrics; Trino stage and operator stats | Scan / exchange / compute |
| $/query (Phase C) | wall time × Σ(node Spot $/h) ÷ 3600 | Spot prices captured at run time and stored with the results |

## 7. Outcome classes

Classification is done by the harness from deterministic rules, never by hand.

| Class | Rule |
|---|---|
| `ok` | Completed, and the result matches the reference |
| `ok_mismatch` | Completed, but the result differs from the reference |
| `err_mem` | Clean memory error: DataFusion `ResourcesExhausted`; Trino `EXCEEDED_*_MEMORY_LIMIT` |
| `err_unsupported` | Planning or feature error (unsupported syntax or function) |
| `err_other` | Any other engine error, with the first error line kept |
| `killed` | Process killed by the OS: `oom_kill` counter incremented or exit code 137 |
| `timeout` | Exceeded the per-query timeout; the query is cancelled |
| `unresponsive` | Health check fails after the query ends or is cancelled |

Errors that no rule recognises are recorded as `err_other` and flagged `unrecognised`.
Reviewing them may add a rule (with a test), after which the run is re-classified by
code. Results are never re-labelled by hand.

B3 also records, per client, whether *other* queries running at the same time
survived an `err_mem`, `killed` or `unresponsive` event.

## 8. Correctness

- **Reference:** Trino's result. Where Trino fails, the result is marked
  `no_reference` and DataFusion variants are compared with each other.
- **Normalisation:**
  - Column names are compared by position.
  - `CHAR` values have trailing spaces stripped.
  - Timestamps are converted to UTC.
  - Decimals are compared at the query's declared scale.
- **Floats:** equal if `|a−b| ≤ 1e-9` or `|a−b| / max(|a|,|b|) ≤ 1e-6`.
- **NULL handling:** NULL equals NULL.
- **Ordering:**
  - Queries without a total `ORDER BY` are compared as multisets.
  - Ordered queries must also match in order, but only on the `ORDER BY` keys.
  - `LIMIT` queries with ties on the sort keys are marked `tie_ambiguous` in the
    query manifest and compared only on the sort-key columns.
- **Rewrites:** queries that needed a per-engine rewrite are listed with the reason
  (dialect, unsupported function). They count towards correctness only if their
  results match.

## 9. Statistics and presentation

- Per query: median of hot runs, cold time, min/max.
- Per suite:
  - Totals over queries that **every** engine completed, with each engine's failures
    listed beside the total.
  - Geometric mean of per-query ratios.
  - Bootstrap 95% confidence interval across iterations.
- Variance flag: coefficient of variation above 10% across hot runs.
- No query is dropped from tables. Failures appear as their outcome class.

## 10. Phase L decision signals (not thresholds)

Phase L feeds a private continue-or-stop decision. These are the signals we expect to
look at; none of them is a pass/fail threshold:
- Ratio of `df` and `dfd` to `trino` on A1/A2 (totals and geomean).
- Completion rate per memory level in B2, and how many failures were `killed` rather
  than `err_mem`.
- A3: how much of the single-node lead remains with 2 workers.
- A6: how much of the gap join ordering closes.
- The pain-point list: the top queries and operators by time lost or failures.

Thresholds for Phase C will be written and published before Phase C runs, with an
explicit note that the authors had already seen the Phase L results.

## 11. Limitations (stated in every report)

- It measures the **foundation** (DataFusion + datafusion-distributed), not Rino.
- **No FTE.** Trino runs with `retry-policy=NONE`; datafusion-distributed has no
  retries. Long-running heavy ETL is out of scope.
- **No writes or row-level DML.** datafusion-distributed has no distributed write
  path, and DataFusion cannot run Iceberg `DELETE` / `UPDATE` / `MERGE`.
- **Phase L is one workstation.** WSL2, x86_64, a local S3-compatible store, loopback
  networking. Results show relative behaviour, not cloud performance.
- **Vendor numbers** from other projects are cited as prior evidence only.
- **TPC-derived.** Not official TPC results and not comparable with published TPC results.
